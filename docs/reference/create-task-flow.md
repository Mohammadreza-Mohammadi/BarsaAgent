# دکمه‌ی «ساخت تسک» — جریان کامل

سند تکمیلی برای BarsaAgent. مکمل سند اصلی، نه جایگزینش.

قیدهای معماری همان‌هاست و اینجا تکرار نمی‌شوند:
UI هیچ‌وقت `.agent-work/` را مستقیم نمی‌خواند یا نمی‌نویسد، هیچ‌وقت `git` اجرا نمی‌کند، و حالت ماندگار مستقل ندارد. هر تغییری از مسیر زیرفرمان‌های `manager.js` می‌رود.

---

## ۱. این دکمه چه کاری می‌کند

از issueهای انتخاب‌شده task می‌سازد، و — اگر تنظیم شده باشد — بلافاصله حلقه‌ی Manager را برایشان شروع می‌کند تا به اولین گیت انسانی برسند.

نکته‌ی مهمی که کل طراحی این دیالوگ را تعیین می‌کند:

> **`request.md` باید متن خام انسان باشد.**

کار Intake این است که متن نامنظم یک آدم را به یک spec با AC شماره‌دار تبدیل کند. اگر ابزار متن را از قبل ساختاریافته یا «تمیز» کند، آن گیت دیگر چیزی را که باید نمی‌سنجد.

پس متن issue به‌عنوان **پیش‌نویس** نشان داده می‌شود، انسان می‌تواند ویرایشش کند، و همان چیزی که تأیید می‌کند عیناً `request.md` می‌شود. ابزار حق افزودن قالب، تیتر، یا Acceptance Criteria ندارد.

---

## ۲. مرحله‌ی الف — دیالوگ ساخت

با فشردن دکمه، **قبل از هر نوشتنی**، یک دیالوگ باز می‌شود.

اگر بیش از یک issue انتخاب شده، دیالوگ به‌صورت stepper است — یکی پس از دیگری، با شمارنده‌ی «۲ از ۵».

### محتوای دیالوگ برای هر issue

| فیلد | مقدار پیش‌فرض | قابل ویرایش |
|---|---|---|
| مخزن مقصد | اگر یکی است، همان؛ وگرنه انتخاب اجباری | بله |
| شناسه‌ی task | از شناسه‌ی issue | خیر |
| slug | از عنوان issue، نرمال‌شده | بله |
| نام پوشه‌ی نهایی | `<id>-<slug>` — فقط برای دیدن | خیر |
| نوع | `task` | `task` \| `spike` |
| متن request | عنوان + متن issue | **بله — این مهم‌ترین فیلد است** |

زیر فیلد متن، یک یادآوری کوتاه بنویس:

> این متن عیناً `request.md` می‌شود. ساده و بدون ساختار بنویس — Acceptance Criteria را Intake می‌سازد، نه تو.

### دکمه‌ها

- **انصراف** — هیچ‌چیز نوشته نمی‌شود
- **رد کردن این issue** — فقط در حالت stepper، می‌رود به بعدی
- **ساخت** — یا **ساخت و شروع** اگر گزینه‌ی شروع خودکار فعال است

### حالت دستی

همین دیالوگ باید بدون issue هم قابل باز شدن باشد — یک دکمه‌ی «task دستی». آن‌وقت شناسه از شمارنده‌ی ترتیبی می‌آید، `source` خالی می‌ماند، و متن request از صفر نوشته می‌شود.

این مسیر لازم است. همه‌ی taskها از issue نمی‌آیند.

---

## ۳. مرحله‌ی ب — ساخت

### قواعد

**ترتیبی، هرگز موازی.** `import-issue` قفل سراسری Manager را می‌گیرد. پنج issue یعنی پنج فراخوانی پشت سر هم.

**شکست یکی، بقیه را متوقف نمی‌کند.** اگر issue سوم خطا داد، چهارم و پنجم ساخته می‌شوند. در پایان یک خلاصه:

```
۴ task ساخته شد
۱ ناموفق: #2044 — قبلاً import شده (task 2044-something)
```

**دکمه در حین اجرا غیرفعال است.** و بک‌اند هم مستقل از UI بر اساس `source.externalId` دوباره‌کاری را رد می‌کند. هر دو لایه لازم است — کلیک دوبار سریع نباید به دو task منجر شود.

### آنچه بک‌اند انجام می‌دهد

برای هر issue:

1. یک فایل موقت JSON بساز
2. `manager.js import-issue --file <tmp>` را اجرا کن
3. فایل موقت را پاک کن
4. شناسه‌ی task ساخته‌شده را از خروجی بگیر

**متن request از فایل می‌رود، نه از آرگومان خط فرمان.** متن فارسی چندخطی با نقل‌قول و کاراکتر خاص، از طریق argv روی ویندوز خراب می‌شود. این یک قید است، نه سلیقه.

شکل فایل موقت:

```json
{
  "repo": "barsa-novin-ray",
  "type": "task",
  "slug": "hex-color-parsing",
  "requestText": "متن خام، عیناً همان چیزی که انسان تأیید کرد",
  "source": {
    "system": "internal",
    "externalId": "2041",
    "url": "https://issues.internal/2041",
    "fetchedAt": "2026-09-06T09:12:00Z"
  }
}
```

برای task دستی، `source` حذف می‌شود و `slug` اجباری است.

### آنچه اسکریپت انجام می‌دهد

`import-issue` پوشه‌ی task را می‌سازد، `request.md` را می‌نویسد، manifest اولیه با `state: new` می‌سازد، یک خط در `events.jsonl` می‌گذارد و **یک commit** می‌زند. UI هیچ‌کدام از این‌ها را خودش انجام نمی‌دهد.

## ۴. مرحله‌ی ج — شروع حلقه

### صف اجرا

taskهای مختلف می‌توانند هم‌زمان اجرا شوند، ولی هر اجرا یک فرآیند claude است. پنج‌تای هم‌زمان هم گران است هم غیرقابل پیگیری.

یک صف با سقف همزمانی بساز:

```yaml
run:
  maxConcurrent: 2
  autoStartOnCreate: true
  autoResumeAfterAnswer: true
```

- taskهای بیشتر از سقف در صف می‌مانند و در UI با وضعیت «در صف» دیده می‌شوند
- سقف در تنظیمات قابل تغییر باشد
- هر task حداکثر یک اجرای فعال — تلاش دوم رد می‌شود، نه اینکه فرآیند دوم بسازد

### `autoResumeAfterAnswer` — مهم‌ترین تنظیم این ابزار

بعد از اینکه انسان یک گیت را جواب داد، ابزار **خودکار** دوباره `run` را صدا می‌زند.

بدون این، هر گیت دو کلیک دارد و بخشی از هدف «حذف کار انسانی» از بین می‌رود. با این، انسان فقط تصمیم می‌گیرد و ماشین ادامه می‌دهد.

پیش‌فرض روشن. هم برای `--approve` و هم برای `--reject` (چون رد کردن هم یعنی نقش قبلی باید دوباره اجرا شود).

## ۵. مرحله‌ی د — گیت‌های انسانی داخل ابزار

اینجا همان جایی است که خواستی «اگر جایی باید نظر بدهم، امکانش داخل ابزار باشد».

حلقه با کد خروج **۱۰** برمی‌گردد و manifest فیلد `awaitingHuman` دارد. UI باید سه نوع را بشناسد.

### `spec-approval`

پنل دو ستونه:

- **چپ:** `request.md` — همان چیزی که خودت نوشتی
- **راست:** `proposed-task.md` — چیزی که Intake ساخت، رندرشده

سؤالی که این پنل باید جواب بدهد: «آیا Intake منظور من را درست فهمید؟»

دکمه‌ها:

| دکمه | فراخوانی |
|---|---|
| تأیید | `manager.js answer <id> --approve` |
| رد | `manager.js answer <id> --reject --reason "<متن>"` |

`--reason` اجباری است. دکمه‌ی رد تا وقتی فیلد دلیل خالی است غیرفعال بماند.

### `clarification`

Architect سؤال پرسیده و کار متوقف شده.

- `questions.md` رندرشده
- یک textarea برای جواب
- کنارش `request.md` و `task.md` برای مرجع

دکمه: **ارسال پاسخ** → `manager.js answer <id> --clarify --file <tmp>`

باز هم از فایل، نه argv.

در UI صریح بنویس که این چرخه **budget مصرف نمی‌کند** — چون spec revision است، نه شکست agent. این جلوی نگرانی بی‌جا را می‌گیرد.

### `merge-approval`

فقط وقتی `autoMerge: false` است.

- `review.md` رندرشده، **هر دو جدولش** — AC و Test Coverage
- خلاصه‌ی diff: فهرست فایل‌ها با تعداد خط اضافه/حذف
- لاگ‌های verification با کد خروج
- `scope.allow` و اینکه آیا `scopeException` وجود دارد

دکمه‌ها:

| دکمه | فراخوانی |
|---|---|
| merge | `answer <id> --approve` |
| رد → پیاده‌سازی | `answer <id> --reject --reason "..." --route implementer` |
| رد → معماری | `answer <id> --reject --reason "..." --route architect` |

دو دکمه‌ی رد جداگانه، نه یک دکمه با dropdown. تفاوتشان واقعی است و باید در UI دیده شود:

- **رد → پیاده‌سازی** یعنی نقشه درست بود، اجرا نه. `implementerRuns` مصرف می‌شود.
- **رد → معماری** یعنی نقشه غلط بود. budget پیاده‌سازی دست نمی‌خورد.

زیر هر دکمه همین یک جمله را بنویس. کسی که ساعت یازده شب دارد رد می‌کند نباید مجبور باشد پروتکل را از حفظ باشد.

## ۶. نقاط یکپارچه‌سازی — فهرست کامل

هر چیزی که ابزار از اسکریپت‌ها می‌خواهد:

| عمل در UI | فراخوانی | خروجی مصرفی |
|---|---|---|
| رفرش برد (هر ۳ ثانیه) | `manager.js status --json` | کل مدل برد |
| ساخت task | `manager.js import-issue --file <tmp>` | شناسه‌ی task |
| شروع / ادامه | `manager.js run <id>` | stream + کد خروج |
| تأیید گیت | `manager.js answer <id> --approve` | کد خروج |
| رد گیت | `manager.js answer <id> --reject --reason <s> [--route <r>]` | کد خروج |
| پاسخ به سؤال | `manager.js answer <id> --clarify --file <tmp>` | کد خروج |
| تایم‌لاین | `manager.js events <id> --json` | آرایه‌ی رویداد |
| دیدن artifact | خواندن فایل داخل پوشه‌ی task، با مسیر محدودشده | متن خام |
| سلامت | `npm run validate-agent-work` | کد خروج + متن |

آخری را در نوار وضعیت نشان بده. اگر قرمز شد، یک هشدار پایدار — نه یک toast که رد می‌شود.

### ترجمه‌ی کد خروج `run`

| کد | نمایش | کار بعدی UI |
|---|---|---|
| ۰ | تمام شد — integrated | کارت به ستون آخر |
| ۱۰ | منتظر توست | باز کردن نشان و افزودن به نوار «منتظر تو» |
| ۲۰ | متوقف | نمایش `blocker` روی کارت |
| ۳۰ | بدون پیشرفت — احتمالاً باگ | هشدار برجسته، این حالت عادی نیست |
| ۱ | خطای اجرایی | نمایش stderr |

کد ۳۰ را مثل بقیه نشان نده. یعنی حلقه یک دور کامل زد و هیچ‌چیز عوض نشد — یک باگ در handler است، نه انتظار.

## ۷. مثال کامل — از issue تا merge

این دقیقاً همان taskی است که به‌زودی به‌عنوان Trial C اجرا می‌شود. ابزار باید بتواند این جریان را نقطه‌به‌نقطه انجام بدهد.

### وضعیت اولیه

در صندوق issue، این ردیف تیک خورده:

```
☑ #2041  رنگ‌های hex سه‌رقمی در نقشه‌ی حرارتی درست کار نمی‌کنند
```

### گام ۱ — دکمه‌ی «ساخت تسک»

دیالوگ باز می‌شود:

```
مخزن:      barsa-novin-ray
شناسه:     2041
slug:      hex-color-parsing
پوشه:      .agent-work/tasks/2041-hex-color-parsing
نوع:       task

متن request:
┌────────────────────────────────────────────────────┐
│ تو نقشه‌ی حرارتی وقتی رنگ رو سه‌رقمی می‌دی مثل      │
│ fff# ناحیه بی‌رنگ می‌مونه. با شش‌رقمی درست کار      │
│ می‌کنه. باید هر دو حالت کار کنه.                    │
└────────────────────────────────────────────────────┘
این متن عیناً request.md می‌شود.

              [انصراف]  [ساخت و شروع]
```

### گام ۲ — ساخت

بک‌اند می‌نویسد:

```json
{
  "repo": "barsa-novin-ray",
  "type": "task",
  "slug": "hex-color-parsing",
  "requestText": "تو نقشه‌ی حرارتی وقتی رنگ رو سه‌رقمی می‌دی ...",
  "source": {
    "system": "internal",
    "externalId": "2041",
    "url": "https://issues.internal/2041",
    "fetchedAt": "2026-09-06T09:12:00Z"
  }
}
```

اجرا:

```
node scripts/manager.js import-issue --file C:\...\tmp-2041.json
```

نتیجه: پوشه‌ی task، `request.md`، manifest با `state: new`، یک commit.

کارت در ستون **ورودی** ظاهر می‌شود.

### گام ۳ — اجرای اول

`autoStartOnCreate` روشن است، پس صف بلافاصله شروع می‌کند:

```
node scripts/manager.js run 2041
```

لاگ زنده در پنل کناری. Manager نقش Intake را اجرا می‌کند، `proposed-task.md` تولید می‌شود، و:

```yaml
awaitingHuman:
  kind: spec-approval
  artifact: proposed-task.md
```

کد خروج **۱۰**. نوار بالای برد: **منتظر تو: ۱**

### گام ۴ — گیت اول

کلیک روی کارت. پنل دو ستونه. سمت راست چیزی شبیه این:

```markdown
## هدف
تابع hexToRgb باید رنگ‌های hex سه‌رقمی را مطابق قرارداد CSS پارس کند.

## Acceptance Criteria
- AC-1: hexToRgb('#fff') باید {r:255,g:255,b:255} برگرداند
- AC-2: hexToRgb('#000') باید {r:0,g:0,b:0} برگرداند
- AC-3: رفتار فعلی برای hex شش‌رقمی بدون تغییر بماند
- AC-4: خروجی هرگز NaN نباشد
```

می‌خوانی، درست است، **تأیید** را می‌زنی:

```
node scripts/manager.js answer 2041 --approve
```

`autoResumeAfterAnswer` روشن است → ابزار خودکار `run 2041` را دوباره صدا می‌زند.

### گام ۵ — معماری، و یک سؤال احتمالی

Architect اجرا می‌شود. اگر حین کار متوجه باگ دوم شود — کلمپ نشدن `t` در `calcHeatColor` که در متن request اسمی از آن نیست — ممکن است `questions.md` بزند:

> در همین فایل، `calcHeatColor` وقتی `value` خارج از بازه‌ی min/max است مقادیر RGB خارج از ۰-۲۵۵ تولید می‌کند. آیا در دامنه‌ی این task هست؟

کد خروج ۱۰، این بار `kind: clarification`.

پنل باز می‌شود، textarea، جواب می‌دهی:

> نه، فقط hex سه‌رقمی. آن یکی را جدا ثبت می‌کنم.

```
node scripts/manager.js answer 2041 --clarify --file <tmp>
```

**هیچ budget ای مصرف نشد.** UI باید همین را نشان بدهد — شمارنده‌ی `architectRuns` روی کارت تغییر نکرده.

اجرای خودکار ادامه. Architect `handoff.md` و `tests.md` می‌سازد، `scope.allow` پر می‌شود، state می‌رود به `ready`.

### گام ۶ — پیاده‌سازی و بازبینی، بدون تو

حلقه بدون توقف ادامه می‌دهد:

- `ready → implementing` — worktree، provisioning، baseline smoke check
- Implementer کد و تست را می‌نویسد
- Manager خودش verification را اجرا می‌کند، گیت scope را می‌زند
- `implementing → review`
- Reviewer اجرا می‌شود (با `before/` که کد قبل از تغییر را دارد)
- Manager جدول شواهد `review.md` را می‌خواند و تصمیم می‌گیرد

در تمام این مدت کارت روی برد حرکت می‌کند و لاگ زنده در دسترس است. **هیچ کلیکی لازم نیست.**

### گام ۷ — گیت merge

`autoMerge: false` است، پس:

```yaml
state: approved
awaitingHuman: { kind: merge-approval, artifact: review.md }
```

پنل باز می‌شود:

```
review.md
  جدول AC:            ۴ از ۴ سبز
  جدول Test Coverage: ۵ Case، همه پوشش داده شده

diff:
  map.utils.ts        +۸  −۳
  map.utils.spec.ts   +۶۴ −۰

verification:
  build  exit 0
  test   exit 0   ۵ passed، ۰ failed
  lint   exit 0

scope: داخل scope.allow — بدون استثنا
```

می‌خوانی، **merge** را می‌زنی:

```
node scripts/manager.js answer 2041 --approve
```

اجرای خودکار: merge با `--no-ff`، تأیید merge شدن، حذف worktree، `git branch -d`، ثبت `mergeCommit`، آزاد شدن قفل‌های scope.

کد خروج **۰**. کارت می‌رود به ستون **تمام**.

### جمع کار انسانی در کل این جریان

سه کلیک تصمیم و یک جمله متن:

1. تأیید spec
2. جواب به یک سؤال
3. تأیید merge

بقیه ماشین بود. **این معیار موفقیت این ابزار است.** اگر برای رساندن یک task به merge بیش از این لازم شد، آن اضافه یک باگ است — یا در ابزار، یا در پروتکل — و باید ثبت شود.

## ۸. خطاها

| حالت | رفتار |
|---|---|
| issue قبلاً import شده | دیالوگ باز نمی‌شود؛ لینک به task موجود |
| اسکریپت کد غیرصفر غیرمنتظره داد | stderr خام نشان داده شود، نه پیام خلاصه‌شده |
| `.manager.lock` گرفتار مانده | نشان بده کدام task و از چه زمانی؛ دکمه‌ی پاک‌سازی **نگذار** — این کار Manager است |
| اتصال به وب‌سرویس issue قطع | صندوق خالی با پیام خطا؛ برد و اجراها بی‌تأثیر بمانند |
| فرآیند `run` وسط کار مرد | کارت به حالت «ناتمام» برود؛ دکمه‌ی اجرای دوباره فعال بماند — حلقه از سرگیری‌پذیر است |
